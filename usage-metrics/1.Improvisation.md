## 4-Table Architecture

### Table 1: `UsageCumulative` (JSON Storage)

**Purpose**: Store cumulative metrics (products, categories, billboards) - one row per user

```prisma
model UsageCumulative {
  id        String   @id @default(cuid())
  userId    String   @unique
  metrics   Json     // { "PRODUCTS": 45, "CATEGORIES": 12, "BILLBOARDS": 8, "STORAGE_GB": 2.3 }
  updatedAt DateTime @updatedAt
  
  user      User     @relation(fields: [userId], references: [id], onDelete: Cascade)
  
  @@index([userId])
}
```

**Example Data**:
```json
{
  "userId": "user_abc123",
  "metrics": {
    "PRODUCTS": 45,
    "CATEGORIES": 12,
    "BILLBOARDS": 8,
    "STORAGE_GB": 2.3
  },
  "updatedAt": "2025-11-30T10:30:00Z"
}
```

**Operations**:
```typescript
// Increment product count (on CREATE)
await prisma.usageCumulative.update({
  where: { userId },
  data: {
    metrics: {
      ...existing.metrics,
      PRODUCTS: existing.metrics.PRODUCTS + 1
    }
  }
})

// Decrement product count (on DELETE only, NOT on archive)
// Note: Archived products still count toward limit
await prisma.usageCumulative.update({
  where: { userId },
  data: {
    metrics: {
      ...existing.metrics,
      PRODUCTS: existing.metrics.PRODUCTS - 1
    }
  }
})
```

**Important Business Logic**:
- ✅ **Increment** on `POST /products` (create new product)
- ✅ **Decrement** on `DELETE /products/:id` (permanently delete product)
- ❌ **NO change** on `PATCH /products/:id` (archive/unarchive product)

**Why archived products still count?**
1. They're still in the database (using storage)
2. They can be unarchived at any time (reactivated)
3. Prevents limit gaming (archive/unarchive to bypass limits)
4. Industry standard (Shopify, Stripe, WooCommerce all count archived items)

### Table 2: `UsageOrders` (Period-Based)

**Purpose**: Track order count per billing period

```prisma
model UsageOrders {
  id          String   @id @default(cuid())
  userId      String
  count       Int      @default(0)
  periodStart DateTime
  periodEnd   DateTime
  updatedAt   DateTime @updatedAt
  
  user        User     @relation(fields: [userId], references: [id], onDelete: Cascade)
  
  @@unique([userId, periodStart, periodEnd])
  @@index([userId, periodEnd])
}
```

**Redis Strategy**:
- Redis key: `orders:{userId}:{periodStartMs}`
- Increment in Redis on every order
- Flush to DB every 5 minutes
- DB is backup + source of truth after flush

interface PeriodDates {
  periodStart: Date
  periodEnd: Date
}

async function getCurrentPeriod(userId: string): Promise<PeriodDates> {
  // Get user's subscription to determine current period
  const subscription = await prisma.subscription.findFirst({
    where: { userId, status: 'ACTIVE' },
    orderBy: { createdAt: 'desc' }
  })
  
  return {
    periodStart: subscription.currentPeriodStart,
    periodEnd: subscription.currentPeriodEnd
  }
}

// Increment order count (Redis)
export async function trackOrder(userId: string): Promise<void> {
  const { periodStart } = await getCurrentPeriod(userId)
  const key = `orders:${userId}:${periodStart.getTime()}`
  
  // Increment in Redis
  await redis.incr(key)
  
  // Set TTL to prevent memory leak (35 days = max period + buffer)
  await redis.expire(key, 60 * 60 * 24 * 35)
}

// Check if user can place order
export async function canPlaceOrder(userId: string): Promise<{
  allowed: boolean
  current: number
  limit: number
}> {
  const { periodStart, periodEnd } = await getCurrentPeriod(userId)
  const redisKey = `orders:${userId}:${periodStart.getTime()}`
  
  // Get count from Redis (hot data)
  const redisCount = await redis.get(redisKey)
  
  // Get count from DB (flushed data)
  const dbRecord = await prisma.usageOrders.findUnique({
    where: {
      userId_periodStart_periodEnd: { userId, periodStart, periodEnd }
    }
  })
  
  // Total = Redis (unflushed) + DB (flushed)
  const totalCount = parseInt(redisCount || '0') + (dbRecord?.count || 0)
  
  // Get user's plan limit
  const plan = await getUserPlanLimit(userId)
  const limit = plan.maxOrders
  
  return {
    allowed: totalCount < limit,
    current: totalCount,
    limit
  }
}

export async function getOrderCount(userId: string): Promise<number> {
  const { periodStart, periodEnd } = await getCurrentPeriod(userId)
  const redisKey = `orders:${userId}:${periodStart.getTime()}`
  
  const [redisCount, dbRecord] = await Promise.all([
    redis.get(redisKey),
    prisma.usageOrders.findUnique({
      where: {
        userId_periodStart_periodEnd: { userId, periodStart, periodEnd }
      }
    })

export async function checkApiCallLimit(userId: string): Promise<{
  exceeded: boolean
  current: number
  limit: number
}> {
  // Cache the limit check result for 1 minute (avoid DB on every request)
  const cacheKey = `api_limit_check:${userId}`
  const cached = await redis.get(cacheKey)
  
  if (cached) {
    const data = JSON.parse(cached)
    return data
  }
  
  // Cache miss - do full check
  const { periodStart, periodEnd } = await getCurrentPeriod(userId)
  const redisKey = `api_calls:${userId}:${periodStart.getTime()}`
  
  const [redisCount, dbRecord, plan] = await Promise.all([
    redis.get(redisKey),
    prisma.usageApiCalls.findUnique({
      where: {
        userId_periodStart_periodEnd: { userId, periodStart, periodEnd }
      }
    }),
    getUserPlanLimit(userId)
  ])
  
  const totalCount = parseInt(redisCount || '0') + (dbRecord?.count || 0)
  const limit = plan.maxApiCalls
  
  const result = {
    exceeded: totalCount >= limit,
    current: totalCount,
    limit
  }
  
  // Cache for 1 minute
  await redis.setex(cacheKey, 60, JSON.stringify(result))
  
  return result
}

export async function getApiCallCount(userId: string): Promise<number> {

    prisma.usageApiCalls.findUnique({

        userId_periodStart_periodEnd: { userId, periodStart, periodEnd }
      }
    })
  ])

## Cron Job Implementation

### Flush Redis to Database (Every 5 Minutes)

```typescript
// app/api/cron/flush-usage-to-db/route.ts

export async function GET(request: Request) {
  // 1. Verify cron secret
  const authHeader = request.headers.get('authorization')
  if (authHeader !== `Bearer ${process.env.CRON_SECRET}`) {
    return Response.json({ error: 'Unauthorized' }, { status: 401 })
  }
  
  console.log('[Cron] Starting usage flush to DB...')
  
  try {
    // 2. Flush orders
    const ordersFlushed = await flushOrdersToDb()
    
    // 3. Flush API calls
    const apiCallsFlushed = await flushApiCallsToDb()
    
    console.log(`[Cron] Flushed ${ordersFlushed} orders, ${apiCallsFlushed} API calls`)
    
    return Response.json({
      success: true,
      ordersFlushed,
      apiCallsFlushed,
      timestamp: new Date().toISOString()
    })
  } catch (error) {
    console.error('[Cron] Flush error:', error)
    return Response.json({ error: 'Flush failed', details: error.message }, { status: 500 })
  }
}

async function flushOrdersToDb(): Promise<number> {
  const pattern = 'orders:*'
  const keys = await redis.keys(pattern)
  
  let flushed = 0
  
  for (const key of keys) {
    try {
      // Parse key: orders:{userId}:{periodStartMs}
      const [_, userId, periodStartMs] = key.split(':')
      
      // Get count and delete atomically (GETDEL)
      const count = await redis.getdel(key)
      if (!count || parseInt(count) === 0) continue
      
      // Get period dates
      const periodStart = new Date(parseInt(periodStartMs))
      const { periodEnd } = await getCurrentPeriod(userId)
      
      // Upsert to DB (increment existing count)
      await prisma.usageOrders.upsert({
        where: {
          userId_periodStart_periodEnd: { userId, periodStart, periodEnd }
        },
        create: {
          userId,
          count: parseInt(count),
          periodStart,
          periodEnd
        },
        update: {
          count: { increment: parseInt(count) }
        }
      })
      
      flushed++
    } catch (error) {
      console.error(`[Cron] Error flushing orders for key ${key}:`, error)
      // Continue with other keys (don't fail entire job)
    }
  }
  
  return flushed
}

async function flushApiCallsToDb(): Promise<number> {
  const pattern = 'api_calls:*'
  const keys = await redis.keys(pattern)
  
  let flushed = 0
  
  for (const key of keys) {
    try {
      // Parse key: api_calls:{userId}:{periodStartMs}
      const [_, userId, periodStartMs] = key.split(':')
      
      // Get count and delete atomically
      const count = await redis.getdel(key)
      if (!count || parseInt(count) === 0) continue
      
      // Get period dates
      const periodStart = new Date(parseInt(periodStartMs))
      const { periodEnd } = await getCurrentPeriod(userId)
      
      // Upsert to DB
      await prisma.usageApiCalls.upsert({
        where: {
          userId_periodStart_periodEnd: { userId, periodStart, periodEnd }
        },
        create: {
          userId,
          count: parseInt(count),
          periodStart,
          periodEnd
        },
        update: {
          count: { increment: parseInt(count) }
        }
      })
      
      flushed++
    } catch (error) {
      console.error(`[Cron] Error flushing API calls for key ${key}:`, error)
    }
  }
  
  return flushed
}
```

## Data Loss Prevention Strategies

### Problem: What if Redis/Server crashes?

**Scenario**: 1000 orders placed → stored in Redis → server crashes → Redis data lost

---

### Solution 1: Redis Persistence (RDB + AOF) ✅ **PRIMARY**

**Redis RDB (Snapshot)**:
```redis
# redis.conf
save 60 1000      # Save if 1000 writes in 60 seconds
save 300 100      # Save if 100 writes in 5 minutes
save 900 1        # Save if 1 write in 15 minutes

dbfilename dump.rdb
dir /data/redis
```

**Redis AOF (Append-Only File)**:
```redis
# redis.conf
appendonly yes
appendfsync everysec  # Fsync every second (balance safety vs performance)
```

**Result**:
- RDB: Periodic snapshots (lose max 5 minutes of data)
- AOF: Every write logged (lose max 1 second of data)
- On restart, Redis restores from AOF + RDB

**Data Loss Window**: Max 1 second ✅

---

### Solution 2: Dual Write (Critical Operations) ✅ **BACKUP**

For orders (business-critical), write to BOTH Redis and DB:

```typescript
// lib/usage-orders-service.ts (modified)

export async function trackOrder(userId: string): Promise<void> {
  const { periodStart, periodEnd } = await getCurrentPeriod(userId)
  const key = `orders:${userId}:${periodStart.getTime()}`
  
  // Write to Redis (fast path)
  await redis.incr(key)
  await redis.expire(key, 60 * 60 * 24 * 35)
  
  // ALSO write to DB immediately (slow but safe)
  // Use background job to avoid blocking request
  setImmediate(async () => {
    try {
      await prisma.usageOrders.upsert({
        where: {
          userId_periodStart_periodEnd: { userId, periodStart, periodEnd }
        },
        create: { userId, count: 1, periodStart, periodEnd },
        update: { count: { increment: 1 } }
      })
    } catch (error) {
      console.error('[Orders] Background DB write failed:', error)
      // Log to error tracking (Sentry)
    }
  })
}
```

**Tradeoff**:
- ✅ Zero data loss (DB always has data)
- ⚠️ Double writes (2x load)
- ⚠️ Slightly slower (but non-blocking with setImmediate)

**Recommendation**: Use for **Orders** (business-critical), skip for **API Calls** (not critical)

---

### Solution 3: Write-Ahead Log (WAL) ✅ **ADVANCED**

For high-throughput scenarios, use a WAL:

```typescript
// lib/wal-service.ts

import { appendFile } from 'fs/promises'

const WAL_FILE = '/data/usage-wal.log'

export async function logToWal(
  type: 'ORDER' | 'API_CALL',
  userId: string,
  timestamp: number
): Promise<void> {
  const entry = `${type}|${userId}|${timestamp}\n`
  await appendFile(WAL_FILE, entry)
}

// Track order with WAL
export async function trackOrderWithWal(userId: string): Promise<void> {
  const timestamp = Date.now()
  
  // 1. Write to WAL (disk, durable)
  await logToWal('ORDER', userId, timestamp)
  
  // 2. Write to Redis (fast)
  const { periodStart } = await getCurrentPeriod(userId)
  const key = `orders:${userId}:${periodStart.getTime()}`
  await redis.incr(key)
  
  // 3. WAL is periodically replayed to DB (every 1 minute)
}

// Replay WAL to DB (cron job every 1 minute)
export async function replayWalToDb(): Promise<void> {
  const entries = await readWalFile(WAL_FILE)
  
  for (const entry of entries) {
    const [type, userId, timestamp] = entry.split('|')
    
    if (type === 'ORDER') {
      await incrementOrderInDb(userId, parseInt(timestamp))
    }
  }
  
  // Clear WAL after successful replay
  await truncateWalFile(WAL_FILE)
}
```

**Result**: Zero data loss (WAL is on disk, survives crashes)

**Complexity**: High (only for massive scale)

### Solution 4: Redis Replication ✅ **PRODUCTION**

Use Redis Sentinel or Redis Cluster:

```
Primary Redis (master)
    ↓ replicate
Replica Redis (slave 1)
    ↓ replicate
Replica Redis (slave 2)
```

**If primary crashes**:
- Sentinel promotes replica to master (automatic failover)
- Data preserved in replicas
- **Downtime**: 30-60 seconds
- **Data Loss**: 0

**Cost**: Higher (need multiple Redis instances)

## Edge Cases & Solutions

### Edge Case 1: Cron Job Fails

**Problem**: Cron job crashes mid-flush, some keys deleted from Redis but not written to DB

**Solution**: Use Redis transactions (MULTI/EXEC)

```typescript
async function flushOrdersToDbSafe(): Promise<number> {
  const keys = await redis.keys('orders:*')
  
  let flushed = 0
  
  for (const key of keys) {
    try {
      // Start Redis transaction
      const multi = redis.multi()
      
      // Get value (don't delete yet)
      const count = await redis.get(key)
      if (!count || parseInt(count) === 0) continue
      
      const [_, userId, periodStartMs] = key.split(':')
      const periodStart = new Date(parseInt(periodStartMs))
      const { periodEnd } = await getCurrentPeriod(userId)
      
      // Write to DB first
      await prisma.usageOrders.upsert({
        where: {
          userId_periodStart_periodEnd: { userId, periodStart, periodEnd }
        },
        create: { userId, count: parseInt(count), periodStart, periodEnd },
        update: { count: { increment: parseInt(count) } }
      })
      
      // Only delete from Redis AFTER successful DB write
      multi.del(key)
      await multi.exec()
      
      flushed++
    } catch (error) {
      console.error(`Error flushing ${key}:`, error)
      // Don't delete from Redis if DB write failed
      // Will retry in next cron run
    }
  }
  
  return flushed
}
```

**Result**: If DB write fails, Redis key preserved → retried in next cron run

### Edge Case 2: Redis Keys Pattern Matching Too Slow

**Problem**: `redis.keys('orders:*')` blocks Redis on large datasets

**Solution**: Use SCAN instead of KEYS

```typescript
async function flushOrdersToDbScalable(): Promise<number> {
  let cursor = '0'
  let flushed = 0
  
  do {
    // SCAN is non-blocking (yields to other operations)
    const [newCursor, keys] = await redis.scan(
      cursor,
      'MATCH', 'orders:*',
      'COUNT', 100  // Process 100 keys at a time
    )
    
    cursor = newCursor
    
    for (const key of keys) {
      // Process each key (same as before)
      await flushSingleOrderKey(key)
      flushed++
    }
  } while (cursor !== '0')
  
  return flushed
}
```

**Result**: Non-blocking, scales to millions of keys

### Edge Case 3: Redis Out of Memory

**Problem**: Redis runs out of memory, evicts keys with LRU policy

**Solution**: Set eviction policy + monitor memory

```redis

```

### Edge Case 4: Database Write Fails During Flush

**Problem**: DB connection lost, upsert fails

**Solution**: Retry with exponential backoff

```typescript
async function flushWithRetry(
  key: string,
  maxRetries = 3
): Promise<boolean> {
  for (let attempt = 1; attempt <= maxRetries; attempt++) {
    try {
      await flushSingleKey(key)
      return true
    } catch (error) {
      console.error(`Flush attempt ${attempt}/${maxRetries} failed:`, error)
      
      if (attempt === maxRetries) {
        // Last attempt failed - log error
        console.error(`Failed to flush ${key} after ${maxRetries} attempts`)
        
        // Send alert
        await sendAlert(`Flush failed for ${key}`)
        
        // Keep key in Redis (will retry in next cron run)
        return false
      }
      
      // Exponential backoff
      await sleep(Math.pow(2, attempt) * 1000)
    }
  }
  
  return false
}
```

### Edge Case 5: Period Boundary (Midnight)

**Problem**: User's billing period changes at midnight, Redis key needs to change

**Solution**: Handle period transitions gracefully

```typescript
export async function trackOrder(userId: string): Promise<void> {
  const { periodStart, periodEnd } = await getCurrentPeriod(userId)
  
  // Check if we're within 5 minutes of period boundary
  const now = new Date()
  const nearBoundary = (
    Math.abs(now.getTime() - periodStart.getTime()) < 5 * 60 * 1000 ||
    Math.abs(now.getTime() - periodEnd.getTime()) < 5 * 60 * 1000
  )
  
  if (nearBoundary) {
    // Near boundary - write directly to DB (avoid Redis key confusion)
    await prisma.usageOrders.upsert({
      where: {
        userId_periodStart_periodEnd: { userId, periodStart, periodEnd }
      },
      create: { userId, count: 1, periodStart, periodEnd },
      update: { count: { increment: 1 } }
    })
  } else {
    // Normal case - use Redis
    const key = `orders:${userId}:${periodStart.getTime()}`
    await redis.incr(key)
    await redis.expire(key, 60 * 60 * 24 * 35)
  }
}
```

### Edge Case 6: Concurrent Cron Jobs

**Problem**: Cron triggers twice (clock skew), two jobs run simultaneously

**Solution**: Use distributed lock

```typescript
// app/api/cron/flush-usage-to-db/route.ts

export async function GET(request: Request) {
  const authHeader = request.headers.get('authorization')
  if (authHeader !== `Bearer ${process.env.CRON_SECRET}`) {
    return Response.json({ error: 'Unauthorized' }, { status: 401 })
  }
  
  // Try to acquire lock (expires in 5 minutes)
  const lockKey = 'cron:flush-usage:lock'
  const acquired = await redis.set(lockKey, '1', 'EX', 300, 'NX')
  
  if (!acquired) {
    console.log('[Cron] Another flush job is running, skipping...')
    return Response.json({ skipped: true, reason: 'Lock held by another job' })
  }
  
  try {
    // Run flush
    const ordersFlushed = await flushOrdersToDb()
    const apiCallsFlushed = await flushApiCallsToDb()
    
    return Response.json({
      success: true,
      ordersFlushed,
      apiCallsFlushed
    })
  } finally {
    // Release lock
    await redis.del(lockKey)
  }
}
```

## Important: Archived Products Business Logic

### Decision: Archived Products Count Toward Limit ✅

**Implementation Rules**:
```typescript
// ✅ POST /api/[storeId]/products (Create)
await checkLimit() // Pre-check
await prisma.product.create({ data })
await incrementCumulative(userId, 'PRODUCTS') // Increment counter

// ✅ DELETE /api/[storeId]/products/:id (Permanent Delete)
await prisma.product.delete({ where: { id } })
await decrementCumulative(userId, 'PRODUCTS') // Decrement counter

// ❌ PATCH /api/[storeId]/products/:id (Archive/Unarchive)
await prisma.product.update({ 
  where: { id }, 
  data: { isArchived: true } 
})
// NO usage counter changes! Archived products still count.
```

### Why This Approach?

**Business Reasons**:
1. **Auto-archiving on sold out**: Products automatically archive when `quantity = 0` (sold out). If we decremented on archive, users could bypass limits by letting products sell out.
2. **Still using resources**: Archived products still stored in database, taking up space.
3. **Can be reactivated**: User can unarchive product when restocking. If we decremented on archive, we'd need to check limits on unarchive (confusing UX).
4. **Prevents gaming**: Users can't archive/unarchive to bypass limits.

**Industry Standard**:
- **Shopify**: Archived products count toward plan limit ✅
- **Stripe**: Archived products count ✅
- **WooCommerce**: Drafts and archived products count ✅
- **BigCommerce**: All products (active/archived) count ✅

**User Perspective**:
```
User has:
- 80 active products
- 20 archived/seasonal products
Total: 100 products (at limit)

Not:
- 80 products (20 don't count) ❌ Wrong
```

### Edge Cases Handled

**Case 1: Product sells out (auto-archived)**
```typescript
// Checkout reduces quantity to 0
await prisma.product.update({
  where: { id },
  data: { 
    quantity: 0,
    isArchived: true  // Auto-archived
  }
})
// Usage counter: NO CHANGE (still counts toward limit)
```

**Case 2: User manually archives seasonal product**
```typescript
// User: "This is a winter product, archive until December"
await prisma.product.update({
  where: { id },
  data: { isArchived: true }
})
// Usage counter: NO CHANGE (still counts toward limit)
```

**Case 3: User restocks and unarchives**
```typescript
// User: "Restocked 100 units, reactivate product"
await prisma.product.update({
  where: { id },
  data: { 
    quantity: 100,
    isArchived: false 
  }
})
// Usage counter: NO CHANGE (was already counted)
// No need to check limit on unarchive ✅
```

**Case 4: User wants to create new product but at limit**
```typescript
// User has 100 products (50 active, 50 archived)
// Limit is 100 products

// Attempt to create new product
const canCreate = await checkLimit(userId, 'PRODUCTS')
// Result: false (at limit)

// Error message: "You've reached your 100-product limit (50 active, 50 archived). 
// Upgrade your plan or permanently delete products you no longer need."
```
