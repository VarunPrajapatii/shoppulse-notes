## Overview

### Approach: Grace Period Method (Recommended) ⭐

**Key Principles**:
- ✅ User keeps full plan features until paid period ends
- ✅ Downgrade scheduled at cycle end using Razorpay UPDATE API
- ✅ After downgrade applies, 5-day grace period activates if usage exceeds limits
- ✅ Auto-archive (not archive, delete) oldest products after grace period
- ✅ Same subscription ID throughout
- ✅ No refund/credit complexity

**Industry Standard**: Netflix, Spotify, Shopify, Heroku, AWS all use this approach

**📝 STATUS: ✅ APPROACH IS CORRECT** — We use the Grace Period Method as recommended here. The "Key Principles" are all implemented except "auto-archive" → we "auto-delete" instead per user's explicit edits in this doc.

## Downgrade Strategy

**📝 STATUS: ✅ IMPLEMENTED** — Grace period logic is in `updated.ts` webhook handler (L70-165) and `enforce-grace-periods/route.ts`. Usage check uses `getOverageSummary()` instead of the `getCurrentUsage()` shown here.

### Why Grace Period?

**Problem Scenario**:
```
Half-Yearly Plan: 100 products, ₹18,000
Current usage: 90 products
Time: 2 months into plan (4 months remaining)
Want to downgrade to: Monthly Plan (50 products, ₹3,500)

Without Grace Period ❌:
- Force user to delete 40 products NOW
- User paid for 100 products for 4 more months!
- Loses business value mid-cycle

With Grace Period ✅:
- Schedule downgrade anytime (no cleanup required)
- User keeps 90 products until paid period ends
- After downgrade: 5-day grace period to reduce from 90 → 50
- Auto-archive (EDIT: delete, not archive) 40 oldest products if user doesn't act
- User can review and restore important ones
```

### Flow Overview

```
User wants to downgrade
  ↓
Schedule downgrade (NO usage validation blocking)
  ↓
Call UPDATE API with schedule_change_at: 'cycle_end'
  ↓
Razorpay stores scheduled change
  ↓
User keeps current plan features (no immediate change) also before 7 days of period end we tell user to start getting under limits via dashboard notifications and email
  ↓
At cycle end: Razorpay applies change automatically
  ↓
subscription.updated webhook fires
  ↓
Check: Does usage exceed new limits?
  ↓
  ├─ NO  → Normal downgrade (update DB, from now the usage flow will work normal as it should be working for the new implemented plan)
  │
  └─ YES → Activate 5-day grace period
            ↓
            Update subscription metadata with grace info
            ↓
            Send grace period activation email
            ↓
            Show dashboard banner with countdown
            ↓
            Send reminder emails (everyday)
            ↓
            Day 5: Cron job auto-archives (EDIT: delete, not archive) excess products, and metrics
            ↓
            Archive (EDIT: delete) 40 oldest products (by createdAt DESC)
            ↓
            Send notification with archived products list
            ↓
            User can restore important products manually
            ↓
            System enforces 50 product limit ✓
```

## Why Store Metadata?

**📝 STATUS: ✅ IMPLEMENTED** — We store extensive metadata including lastDowngradeAttempt, downgradeMethod, scheduledDowngrade info, and gracePeriod data. This section accurately describes the value of metadata tracking.

### Question: Why track `lastDowngradeAttempt` and `downgradeMethod`?

**Answer**: Debugging, analytics, and audit trails

#### Use Cases:

**1. Debugging Support Issues**
```typescript
// Customer: "I tried to downgrade but it didn't work"
// Support checks metadata:
{
  lastDowngradeAttempt: "2025-11-20T10:30:00Z",  // When they tried
  downgradeMethod: "UPDATE_API_SCHEDULED",        // How we processed it
  scheduledDowngrade: {
    willExceedLimits: true,                       // Why grace period activated
    currentUsage: { products: 90 },
    newLimits: { products: 50 }
  }
}
// Support can see exactly what happened and when
```

**2. Analytics & Business Intelligence**
```typescript
// Questions we can answer:
// - How many users schedule downgrades but cancel them?
// - What's the average time between scheduling and effective date?
// - Do users who exceed limits keep their subscriptions longer?
// - Are downgrades seasonal?

const downgradeAnalytics = await prisma.subscription.findMany({
  where: {
    metadata: {
      path: ['lastDowngradeAttempt'],
      not: null
    }
  }
});
```

**3. Fraud Detection**
```typescript
// NOTE: this is important to implement
// Detect suspicious patterns:
// - User downgrades/upgrades 10 times in a day
// - User schedules downgrade, immediately cancels, repeats

const suspiciousActivity = metadata.downgradeHistory?.length > 5;
```

**4. Feature Flag Migration**
```typescript
// We try new downgrade method, track which method was used
if (metadata.downgradeMethod === 'OLD_CANCEL_CREATE') {
  // Migrate to new method
} else if (metadata.downgradeMethod === 'UPDATE_API_SCHEDULED') {
  // Already on new method
}
```

**5. Compliance & Audit**
```typescript
// Legal requirement: Track all subscription changes
// Metadata provides immutable history of what happened and when
```

### Same Reasoning for Upgrade Flow

**`lastUpgradeAttempt`** and **`upgradeMethod: 'UPDATE_API'`**:
- Track when user upgraded
- Verify UPDATE API vs old method
- Calculate time-to-upgrade metrics
- Support: "I upgraded but didn't get charged correctly"
- Analytics: "Do users upgrade after trial or mid-cycle?"

### Metadata is Cheap, Insights are Valuable

- Storage cost: ~100 bytes per subscription
- Value: Priceless for debugging, analytics, compliance
- Best practice: Track more rather than less
